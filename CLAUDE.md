# dominickdominick.com — notes for Claude

A personal site on a Cloudflare Worker + D1 (database) + R2 (media): a home page, the Studio (a music maker in the browser) and two password-protected study modules, with a slim admin for editing the home page. The owner is the only admin. `README.md` is the user-facing description; this file is what you need to work here quickly. The site used to be much larger (articles, projects, search, a circuit simulator, 3D scans, a photo editor, an aim trainer and more) and was cut down on 2026-10-08; the old code is in the git tag `before-slim-down` and the story is in `outline.md`.

## Run it

```bash
npm install
npm run db:local                 # local database: schema, migrations and the home page (seed/home.sql)
npm run dev                      # local site at http://localhost:8787, admin at /admin
npx wrangler d1 execute DB --local --command "select …"   # poke the local database
```
`.dev.vars` holds `ADMIN_PASSWORD` and `SESSION_SECRET` (gitignored; copy `.dev.vars.example`). Never print them or paste them anywhere. Static files in `public/` are served straight from disk, so a browser reload picks them up; Worker code reloads by itself. Node 22 or newer (`.nvmrc`). The `package.json` has no `"type": "module"` on purpose: several tests load the browser scripts as plain scripts.

## Testing (do this before every commit)

**Check only what the change can break. Every run costs the owner money.** A CSS or copy change gets `npm test` (a few seconds) plus the few browser tests for the area touched (`node tests/e2e/run.mjs studio_`), never the full browser run. The full run and the audits are for changes to the worker, the data, or something shared by much of the site. A failure that plainly comes from the sandbox (empty local database, no home page, no CDN or internet) is noted, not investigated, and not compared against older commits.

```bash
npm test                              # all pure tests. `node tests/run.mjs song` filters by name.
node tests/e2e/run.mjs                # all browser tests, parallel. `node tests/e2e/run.mjs studio_` filters by name.
node tests/e2e/run.mjs --live test_x  # one test against the dev server already running on :8787 (fast, but changes that database)
```
- The e2e runner starts its own throwaway servers on copies of the local D1/R2, so tests may create and delete freely and the dev database is untouched (it needs `npm run db:local` once, so there is a home page). It prints only **new** failures: tests that already failed are in `tests/e2e/known-failing.txt` (fix one, delete its line). A test that fails under load is retried once on its own and reported as "Flaky" if it then passes (`--no-retry` turns that off). First time on a machine: `cd tests/e2e && npm install && npx playwright install chromium`.
- **Don't edit `worker/` or `public/` while a test run is going** (the servers reload mid-test and make false failures).
- A new feature gets a node test (`tests/<name>.test.mjs`, must print `ALL PASS`; copy the style of a neighbour) for its pure logic, and a browser test (`tests/e2e/test_<name>.js`, copy a neighbour: it uses `E2E_BASE` and `ADMIN_STATE`) for the UI.
- Three by-hand audits (not tests, run them after a UI change and read the report): `node tests/e2e/audit/audit-apps.js` (the Studio on a phone and a computer, dark and light: overflow, off-screen parts, axe, controls under 24 px), `node tests/e2e/audit/audit-public.js` (every public page: SEO, axe, overflow, links, weight) and `node tests/e2e/audit/audit-admin.js` (every admin tool, its tabs and dialogs: axe, overflow, tap targets, focus, Esc; `--only features-btn` for one tool). All three need `wrangler dev` running on :8787 and only open and close things. Expect 0 high / 0 medium.
- A browser test that adds an admin dialog should also run axe (see `test_block_bar.js`) in dark and light, and check a 390 px width.
- Test data is synthetic (prefix titles with `QQ`). If you must use `--live`, clean up what you made.
- Before saying a failure is "not mine": check it on the previous commit (`git stash`/checkout, run that one test, restore).
- The pure tests treat code that only a test uses as a smell, not a rule: `tests/features.test.mjs` (the board's validator) and `tests/backup-coverage.test.mjs` (every table is backed up or on the "not backed up" list) guard data on purpose.

## Git, pipeline and deploy

`main` is the live site, trunk-based: work on a short-lived branch, open a pull request, merge when CI is green. There is no `production` branch and no per-session branches. The full description and the one-time setup (the Cloudflare secrets, switching off Cloudflare's own build, why there is no branch protection) are in `outline.md` section 0; read it before changing a workflow.
- **A pull request** runs `.github/workflows/ci.yml` (every script parses, `npm test`, `wrangler deploy --dry-run`, and the browser tests when site code changed) and `.github/workflows/preview.yml` (a preview address on the pull request, from the separate preview database and storage).
- **A push to `main`** runs the checks and then ships: the `deploy` job needs them green, runs `wrangler deploy`, runs `scripts/smoke.mjs` against the live site and `wrangler rollback` if that fails. It refuses to deploy while a database migration is waiting. Without the Cloudflare secrets the deploy and preview jobs **skip with a notice** (they do not fail) and the `verify` job smoke-tests whatever Cloudflare's own build deployed.
- **`monitor.yml`** smoke-tests the live site every six hours and opens one issue if it fails.
- **Migrations** go through `.github/workflows/migrate.yml` (manual; you must type `migrate production`; takes a backup first). Production D1 changes (migrations, data fixes) need the owner's explicit say-so each time. Never run `seed/home.sql` against production. Never touch the live site or call external services from tests. Local dev only.
- **A change to a workflow is checked by reading it twice**, because it cannot be run here: keep every step that needs a secret behind the `ready` check, keep `permissions` as small as the job allows, and pin actions to a major version.
- **Windows:** the repo is developed on Windows and Linux. Do not add `new URL(...).pathname` for file paths (use `fileURLToPath`) and start `npx`/`npm` with `shell` and `windowsHide: true` (see `tests/e2e/run.mjs`). Do not leave a `wrangler dev` running while editing files: it restarts its server on every change.
- **Commit messages are a plain bulleted list of the changes and nothing else**: no attribution or co-author lines, no session links, no tool or model names, in commits, code comments or any repo file. Commit only files you changed for the task (`git add <paths>`, not `-A`). Never force-push (the one rewrite of history, on 2026-10-08, was the owner's explicit instruction).

## Rules that have bitten before

1. **D1 allows 100 bound variables per statement.** Chunk big `IN (…)` lists (`chunkList`, `selectIn`, `updateIn` in `db.js`, 90 per chunk).
2. **Settings rows are the schema-free store.** Small things live in the `settings` table (the five site settings, the daily backup status), so no migration is needed and backups (`exportAll` dumps every settings row) include them. `PUT /api/admin/settings` writes every key in `SETTINGS_KEYS` and saves a missing one as empty.
3. **Anything that animates in the public CSS must sit inside `@media (prefers-reduced-motion: no-preference)`** (`tests/reduced-motion.test.mjs` fails otherwise).
4. **The CSP has no `unsafe-eval`.** No `eval`/`new Function` anywhere in browser code. The CSP also allows no CDN: everything is served from the site (`worker/index.js` `SECURITY_HEADERS`).
5. **Audio plays only after a click** (the builder's `ensureAudio()`). Never autoplay.
6. **A new file that public visitors need while the site is in maintenance mode** goes in `MAINTENANCE_EXEMPT_FILES` in `worker/index.js`.
7. **Every admin dialog** is a `.modal` with `role="dialog"`, a `close-…` button (Esc and backdrop click press it), and is added to the Ctrl+S map near "Keyboard shortcuts" in `app.js` if it has a Save. Dialog stacking and focus return are handled for you (`modalFocusReturn`).
8. **Saves that can race** use `expected_version` (`checkConflict`). Autosave must never publish a draft by itself.
9. **Text from users or from scripts is data.** Escape with `escapeHtml` in admin templates; the public side goes through `worker/text.js` / `render.js` helpers.
10. **Server validation in a small pure file, then called from the route**: keeps it testable and keeps `admin-api.js` readable.
11. **No emoji anywhere on the site** (the owner's rule, public and admin, and in `outline.md` / `features.json`). That includes symbols phones draw as emoji (play, pause, stop, record, the north-east arrow, warning sign): use words, or a drawn icon from `worker/ui-icons.js` (`uiIcon(name)`; `.ui-icon` in `public/style.css`). Plain text marks (✓ × ← → ♪ ©) are fine. `tests/no-emoji.test.mjs` fails on any, escapes included; a line that only holds one as data is marked `// no-emoji: data` and uses an escape.
12. **The Studio is independent of the admin.** Its dialogs are `public/studio/dialogs.txt` and its CSS is `public/studio/studio.css` (every selector starts with `.app-native`; it was generated once from the old admin stylesheet and is edited by hand now). A new Studio style goes in `studio.css` under that scope; a new element the scripts look up by id goes in `dialogs.txt`. `tests/studio-ids.test.mjs` fails when a script asks for an id that exists nowhere, and `tests/app-pages.test.mjs` checks the dialogs.
13. **The database still has the tables of the deleted features.** No code reads them; the daily backup still saves them. Dropping one is a production database change (outline.md section 3).

## The redesign (Bit bento): read this before the older sections below

Some sections further down describe the design before this one; where they disagree, this wins.
- **Look:** Bit bento. Ink on paper, Mac-style windows (title bar, close box, stepped corners, dithered shadow), pixel type (Silkscreen for labels, VT323 for body; self-hosted in `public/fonts/`, listed in `MAINTENANCE_EXEMPT_FILES`) and **one tiny accent, orange `--orange` (#ff6a1a)**: playhead, record, lit dial tick, focus ring, current state. Never as text colour (about 2.9:1 on paper). The tokens are `body { … }` in the "Bit bento" block of `public/style.css`; `--accent` is the ink and `--on-accent` the paper. Because they are set on `body` they beat whatever is on `:root`, which is why the old Appearance settings (accent, fonts, control presets) were deleted: they had no effect.
- **Soft palette (2026-10-08):** the first version was pure `#000` on `#fff` and inverted, which was hard on the eyes. Light is ink `#2a2622` on paper `#f5f0e6`, dark is ink `#e3ded2` on paper `#18161b`, dim text `#675f55` / `#a39d91`; contrast is about 12:1 (checked: dim text about 5.5:1). The `.page` ground is a dot grid tinted with 16% of the ink (`color-mix`), not full-ink lines, so it does not shimmer. Change colours only in that token block (and the matching `theme-color` values in `render.js` and `nav.js`, the favicon in `render.js`, the maintenance and error pages). Print stays pure black on white.
- **The public site is the home page and the Studio** (`worker/site-scope.js` decides which addresses are public; everything else is the 404 page).
- **The nav is the camera dial described below**: three stops, studio, home (in the middle) and settings. The stops are all the same size; only the one under the needle is lit. The last stop opens the **Settings dialog** (`#site-finder`, built by `finderHtml` in `render.js`, driven by `nav.js`; the ids are historical): dark/light, reduce motion, text size and links to the pages; Ctrl/Cmd+K opens it, arrows move, Esc closes. There is no search.
- **The Studio** (`song-studio.js`, "the display" and `placeSound`): the transport row is the **display** at the top (Play, Stop, Rec, a readout of position and tempo, the named switches click / snap / follow / from top / volume, Undo, Redo); there is no fan (`NO_FAN`). On a phone the switches sit beside Hold and Play over the keys. On the Studio page the Tools sheet is **docked** (`dock`): from 1280 px it is the inspector in the right-hand panel (its tabs a small dial), below that it is the bottom **deck**, where `.studio-deck-dial` picks pads (the keys) or a pane. The owner's admin dialog keeps the sheet and its Tools button. The open track's row no longer repeats Mute (each playlist row has its M); the hint paragraphs are hidden.

## Songs: how a song is stored

A song is one JSON blob. A visitor's songs live in their own browser (`localStorage`, key `studio.songs.v1`, see "The Studio page"); the admin's old D1 song library is gone (the `songs` table is still in the database, untouched). The sound is made by `public/song-engine.js` (shared by the builder and the Studio), the editor is `public/studio/song-builder.js`, and `public/studio/song-files.js` is the pure helper for MIDI, JSON import/export and import cleaning. A song is never put on a web page (there is no embed, player look, theme or page sync); a song saved long ago may still carry `visualization`, `theme`, `page_sync` or `cached_peaks`, which `cleanSong` ignores and the builder drops when it opens the song.
- **A new song field has to be added in three places or it silently disappears:** the engine (`scheduleStep` or a send like `setSpace`), `song-files.js` (`cleanSong`, or import drops it), and `song-builder.js` (open, undo restore in `applySongHistoryState`, the control). Add the field to `tests/song-files.test.mjs`'s "exactly the builder's own keys" list only if it is written for every song; optional fields (voice, patterns, chain, editing) are written only when set, so old songs and their noise seed stay identical (`tests/song-chain.test.mjs` pins the seed values).
- **A song has a format version** (`SONG_VERSION` in `song-files.js`, stamped by `cleanSong`, set on new songs by `defaultSongData`; the version of the song FILE wrapper is the separate `VERSION`). The song format may change freely while the Studio is being built (the owner keeps no songs yet), but a song saved by an earlier build must still open: when a change needs old songs reshaped, bump `SONG_VERSION` and add a step to `migrateSong` (oldest first); a field that is simply gone is dropped by `cleanSong` with no migration. `tests/song-version.test.mjs` covers it.
- **Patterns:** the pattern being edited is always the song's own `tracks`, `melody.notes` and `melody.ties` (every editing tool works on it unchanged); `editing` names it (absent = "A") and `patterns` holds the others as `{tracks, notes, ties}`; `chain` is the song order (up to 32 letters). Mix, instrument, scale, tempo, echo and the rows themselves (`trackMeta`) are shared. Resolve patterns only through the engine's `patternData` / `chainOf` / `viewOf` (and `chainParts` in song-files.js, kept equal by a test), never by reading `songData.tracks` for "the song".
- **Extra melodic parts (bass, chords, lead):** `bass`, `chords` and `lead` are each `{notes, ties, voice, volume, muted, hidden}` with the same shape as `melody`, over a two-octave roll of their own (bass C1 to B2, chords C3 to B4, lead C4 to B5; melody is C3 to B4), with default voices bass, pad and lead. The engine keeps them in one registry (`PART_KEYS`, `PART_NOTES`, `PART_OCTAVES`, `partVoiceOf`, `isPartMuted`); `song-files.js` loops the same keys, so a fourth part is a one-line addition in each. A part is absent until used (the builder creates it in memory with `ensurePart(key)` and `pruneParts()` drops an empty, uncustomised one at save, so old songs are stored unchanged and the engine's noise seed only includes parts that have notes). The open pattern's part is `songData[key].notes/ties`, every other pattern's is `patterns[X][key] = {notes, ties}`, and it follows the same three-places rule. In the builder the piano roll shows one part at a time (`rollPart`, `roll()`, `rollNotes()`), so every roll tool works on any of them; never read `songData.melody` in code that should also serve the other parts. A MIDI file writes bass, chords and lead on channels 2 to 4 (own tracks named Bass, Chords, Lead; the chords and lead tracks carry a marker text event so our own file re-imports into the right part); a foreign track named "bass" or one mostly below C3 becomes the bass.
- **Bars, lanes, sound tweaks:** `bars` (1 to 64, absent = as long as the music) is the song's length; `lanes` is `{ drums|bass|chords|melody|lead: { order: ["A","B"], loop: false } }`, a run of patterns for one track (a track with no lane follows the song order `chain`; a lane shorter than the song loops until it ends unless `loop` is false). There are 16 patterns (A to P) and the order is at most 64 bars. The engine resolves it with `songBars` / `laneOrder` / `patternAtBar` / `barView` (the song as it sounds in one bar; `viewOf` when there are no lanes), the player reports `info.patterns` (the pattern each track plays now) and `currentPatternFor(track)`, and `song-files.js` `chainParts` is kept equal by `tests/song-chain.test.mjs` and `tests/song-lanes.test.mjs`. A part (and melody) can carry `synth`, a few clamped tweaks laid over its named voice (`Engine.cleanSynth`; the same ranges are in `song-files.js`). `scale` may carry `snap: true` (notes played or tapped move to the scale).
- **Sounds:** the instruments are `MELODY_VOICES` in the engine (grouped for the menus by `VOICE_GROUPS`; the builder fills `#song-voice`, `#song-bass-voice`, `#song-part-voice` and `#song-kit` from the engine at start, so a new voice or kit is added in the engine, and in `song-files.js` (`MELODY_VOICES`, `KITS`; a test keeps them equal); the first five voices and three kits are pinned, their numbers never change). Kits are `KIT_PARAMS` over `DEFAULT_KIT` (a kit only names what differs; `KITS` is the menu order because number-like names sort first in an object). A voice may use `unison`, `sub`, `partial`, `noise`, `drive`, `fm`, `tremolo`, `vibrato`, `wobble`, `slide`, `ftype` and a filter sweep; these parts are only built when asked for. A track's `synth` tweaks (`SYNTH_RANGES` + `ftype`) are mirrored in `song-files.js`. One drum sound's own `tune`, `decay` and `tone` live in `trackMeta[row]` (`DRUM_RANGES`, `drumShape`, `kitParams`; mirrored in `song-files.js`). A new knob is added in all of those and in the Studio's `KNOBS`.
- **Audio wakes from a tap:** a phone keeps the sound asleep, so everything that makes a sound calls the builder's `ensureAudio()` first (Play, Preview, keys, pads). Do not add a new sound path that calls `getAudioCtx()` alone.
- **Output limiter:** everything audible ends at one soft limiter in front of the speakers (`getOutput` in `song-engine.js`: a quarter-gain into a 4097-point waveshaper; the master bus, the Space return and the Echo return all connect to it, never to `ctx.destination`). Below 85% of full scale it is a straight line (a normal mix is untouched); above that it bends towards full scale and never passes it, so a hot mix is squashed, not clipped. The meters and the clipping history read the signal before it, so they still say when a mix is hot. A context flagged `ctx.__measure = true` (the peak scan behind Normalize to peak, `renderWaveformPeaks`) gets no limiter and sees the true level; the audio export is limited. The metronome click goes straight to the destination on purpose (it is not part of the song). A test that looks for "the node that feeds the output" uses `reachesOutput`/`limiterIn` from `tests/fake-audio.mjs`; `count(ctx, "shaper")` does not count the limiter. `tests/song-limiter.test.mjs`.
- **Steady playback:** the player (`createPlayer` in `song-engine.js`) schedules steps a little ahead of the audio clock from a timer. If a busy page runs the timer late (the next step's time is already over by more than `STALL_S`) it skips the steps that are over, keeps its position in the song true to the clock (`advance`), counts the stall and looks further ahead for a while (`ahead`, 0.1 s up to `MAX_AHEAD_S` 0.3 s, easing back after `CALM_S` of steady running); `player.stalls()`, `skippedSteps()` and `lookahead()` report it. It never plays missed steps in a burst. The builder wakes a suspended or interrupted sound when the page is visible again and on `pageshow`. The echo's delay time glides to a tempo change (`setTargetAtTime`). `tests/song-timing.test.mjs`.
- **Recording lands where it was heard:** `recordingSpot` places a press with `SongLive.pressTime(ctx, stamp)` (pure): the audio-clock time of the press taken from `ctx.getOutputTimestamp()` (a MIDI message's own `timeStamp`, kept in `pressStamp` while `handleMidiMessage` runs, or `performance.now()` for a key or pad), so the wait in the page's event queue and the output latency are both allowed for; without that it takes off the reported output or base latency. Never more than 0.25 s from the render clock. `tests/song-press-time.test.mjs`.
- **Recording helpers:** `quantizeSteps` (0, 1, 2 or 4; `localStorage.songQuantize`) moves a recorded note to the nearest grid line in `recordingSpot`; the Studio keeps `followOn` (`songFollow`) and `recTop` (`songRecTop`: arming Rec, or Play while armed, starts from the top).
- **Pump** (`pump`, 0 to 100, absent when off) ducks all the music (melody, bass, chords, lead) on every kick: with it on, `scheduleStep` routes `scheduleMusic` through a per-context music bus (`withMusicBus`) that `duckMusic` automates. With it off nothing extra is built, so graphs and seeds are unchanged (`tests/song-pump.test.mjs`).
- Drum rows: the four core rows always exist; open hat, rim, tom and crash exist once added (found by their `trackMeta` entry). Melody instruments are `melody.voice` (absent = the plain waveform note).
- Test helpers: `tests/fake-audio.mjs` (recording Web Audio stand-in plus engine and song-files loaders). A browser test can see which pattern is sounding by wrapping `SongEngine.createPlayer` in an init script.

## Song Studio view

`public/studio/song-studio.js` is the Song builder's only UI, built for a phone first. Top to bottom: **the playlist** (below), the open track (one row of controls: which bar it is editing, + Bar, Loop, Steps or Roll, the sound named on its button, Mute, Clear and a ⋯ menu with Track tools, the bar actions and the song length; on a phone Loop, Mute, Clear and MIDI move into that menu), the steps or roll filling what is left (the only part that scrolls; a phone shows half a bar of steps at a time with a "Steps 1–8 / 9–16" pager and snap scrolling, and opens note tracks in the Roll), the transport (Play, Stop, Undo, Redo on a wider screen, the Rec hub with its fan, BPM), and the keys or pads at the bottom. A phone on its side puts the transport and keys in a column on the right. The track counts are what each track plays in the bar picked for it (`cardInfo`), not the open pattern. **Tools** (top bar) opens a sheet with six tabs: Sound (the open track's instrument, a Wave and sliders for attack, decay, sustain, release, brightness, thickness and vibrato; for Drums the kit, one chosen sound's volume and mute, add a sound), Track (the builder's own tools for the open track and the scale with Snap), Song (tempo, length, swing and the rest, metronome sound, mix, notes, templates), Patterns (the builder's arrangement section), Share (clipping history and the exports) and MIDI (connect a keyboard, test its keys). The old "classic" editor can still be switched on with `localStorage.songView = "classic"`, but only so the older browser tests (which the runner seeds with it) keep driving it; nothing offers it.

**The playlist** (`#studio-stack`, `renderStack` in `song-studio.js`) is the five tracks as rows, the way a DAW lays them out (the owner asked for "tracks like FL Studio", with the five kept): each `.studio-card` row has a header on the left (`.studio-pl-head`: number, name, count and sound on a wide screen, and an **M** button, `data-mute`) and its bars as clips on a timeline (`.studio-pl-lane`, one `button.studio-clip[data-clip][data-track][data-bar]` per bar of the song from `arr.info(track).cells`: a small picture of that bar's pattern, its letter, dashed when the loop repeats it, empty when the track is silent there). A ruler on top numbers the bars (its ticks carry on past the end by a background); a line (`#studio-playhead`, `--ph` in bars, set in `paintStep`) crosses the rows while the music plays and `.is-now` lights the sounding bar in every row. The timeline scrolls sideways with the headers and ruler sticky (`position: sticky`), bars are a fixed width (`--pl-bar`: 56px phone, 84px wide), so the repeating guide lines in the lane background line up. A tap on a clip opens that track in that bar (`pickBar`: `barPick[track]`, `arr.openBar`), a tap on a header or on the empty part of a lane opens the track (`selectTrack`), **M** mutes without taking the editor away from the open track (`muteRow` opens the track for a moment because the builder's mute buttons act on the open one, then goes back), arrow keys go along a row and between tracks. The open track's row is `data-pos="front"` (above/below for the rest) and its open clip is ringed. There is no swiping or wheel-turning through the tracks any more. The rows are `--pl-row` high (30px; 24px on a phone on its side); with less room than five rows the playlist shrinks (phone: flex-shrink, wide: the grid row is `minmax(1.5 rows, auto)`) down to a row and a half and scrolls up and down (`revealRow` brings the open track's row into view, the ruler is sticky), and the open track never gets less than `--detail-min` / 250px, so the Studio scrolls instead. `#studio-stack` carries `data-no-history` (a tap there is not an edit). A cell in the lanes is a button or the lane itself, so tests tap a row by `#studio-stack .studio-card` (its middle is the lane) and a clip by `[data-clip][data-bar]`; the old bar strip in the open track is gone (`#studio-bars` no longer exists; `#studio-editing` names the track and bar being edited). `tests/e2e/test_studio_playlist.js` covers it.

**Folding and sizing the open track** (`syncFold`/`setFolded`, `setEditorH`/`editorMax`, the `#studio-split` handle, all near "folding and sizing the open track" in `song-studio.js`): `#studio-fold` (first button of the open track's row) folds the editor to that one row (`.studio-editor-folded` on `.song-studio`, `data-folded` on `#studio-detail`; the playlist takes the room and its rows grow up to 72px), kept in `localStorage.studioEditorFold`. `#studio-split`, a focusable `role="separator"` between the playlist and the open track, sets the open track's height on a phone and on a wide screen (not on a phone on its side): drag (pointer events with capture), arrow keys (24px a step), Home/End, Enter or two quick taps to go back to automatic. On a phone it is a flex child; on a wide screen it shares the playlist's grid cell (`grid-area: stack`, on its bottom edge) and a chosen height turns the grid into `... minmax(var(--pl-min), 1fr) var(--detail-h) ...` (`data-detail-h`), so the playlist takes what is left. **It is a magnet:** within 14px of a height that means something (`magnetPoints`: as short as it goes, the playlist showing all five tracks, as tall as it goes, the automatic height) the edge is pulled onto it, the grip widens and lights orange and the choice is announced; Alt held down turns the pull off; the pull is recomputed from the pointer on every move, so pulling away releases it. `editorMax()` / `editorFloor()` (wide: the playlist stops growing at five rows of 72px, so the open track never gets less than what leaves it that) keep the keys on the screen. The height is `--detail-h` on `.song-studio` (with `data-detail-h`), kept in `localStorage.studioEditorH` (0/empty = automatic, minimum 150px; a kept value is applied as it was on load and resize). `tests/e2e/test_studio_fold.js` covers it.

It stores nothing and is a view over the builder's own editor, which stays in the page, hidden. **The five tracks are fixed and in this order, 1 Drums, 2 Bass, 3 Chords, 4 Melody, 5 Lead** (the owner asked for a set order that cannot be changed or extended; do not add a way to add, remove or reorder them); each is also the name of its lane. They are a grouping of the song's own data: Drums is every drum row in one grid (with pads for keys), the others are the `bass`, `chords`, `melody` and `lead` parts, each on its own roll. The step cells are a mirror painted from `songData`, and every control drives the builder's: a tap clicks the matching step (`#song-sequencer` / `#song-piano-roll`), choosing a note track clicks the `#song-roll-<part>` button so the real roll shows that part, sliders and menus set the matching control and fire its event, play is `#song-play`. The sheet **moves the builder's own controls into it, ids and all** (`buildSheet`), so they keep working; the selects the Sound tab drives (`#song-voice`, `#song-bass-voice`, `#song-part-voice`, `#song-kit`, `#song-waveform`) stay hidden in the builder. A card counts a held (tied) step as part of the note before it, not as another note. The Roll draws by dragging (`host.group(true/false)` makes the whole drag one undo step).

**Editing the grid (sequencer and roll):** the maths is in `public/studio/song-edit.js` (`window.SongEdit`, pure, `tests/song-edit.test.mjs`): a roll's notes are *spans* (a note and the steps tied to it, `spans`/`spanAt`), moved or copied together (`move`, cut back so the group keeps its shape), resized (`resize`, never over the next note), re-levelled (`setLevel`, `level`: 1 is stored as `true`, below it a number from 0.1), picked by a box (`inBox`), and drum steps painted (`paintCells`). The Studio applies them through `SongStudioHost.editRoll(fn)` / `editDrums(fn)` (fn gets copies and returns the new data; one undo step unless a drag already holds a `group`) and `stepStrength()`; never write `songData` from the Studio any other way. Interactions in `song-studio.js`: drum steps paint by dragging (`drumDown`), notes move/resize/Alt-copy by dragging (`rollDown`: the right 40% of a note's last step is its resize handle), Shift-drag on empty steps is a box (Shift on a note stays the builder's tie toggle), Ctrl/Cmd-click toggles a pick, with notes picked the arrow keys move them (Shift: an octave or a beat), Delete removes, Ctrl+A picks all, Esc lets go. The **strength lane** is a row of `.studio-lane-bar` at the bottom of the grid (it lives inside `#studio-grid` so it lines up with the steps; hidden on a phone): drums edit the sound in `soundRow`, the roll edits the picked notes or every note starting on that step. Snap (`studioSnap`: 1/16, 1/8, 1/4) and zoom (`studioZoom`) are the roll's own, stored in localStorage; other tracks' notes show as `.ghost` dots; bar tools (shift earlier/later, copy, paste) are in the track's ⋯ menu. A drag that changes the data goes through `host().group(true/false)` and then `suppressClick()` so the click that follows a drag is ignored. The roll is still the builder's two octaves of sixteen steps per bar (a longer range or a per-track step length would mean changing the song format).

**Playing live (keys and pads):** `public/studio/song-live.js` (`window.SongLive`, pure, `tests/song-live.test.mjs`) holds the rules: `rateSeconds`, `arpCycle`/`arpPick`, `chordNotes`/`strumPlan`, `padVelocity`/`rollVelocity`, `bendCents`, `cleanPlay` (settings kept in `localStorage.studioPlay`). The sound side is the engine's `playVoicedNote(..., random, live)` (returns `{ release, bend }`; a live note is held up to 30 s, and a song's own scheduled notes ignore all of it) and `playLiveWave` for the plain waveform; the builder host adds `noteOn(name, velocity)` (a held note; while recording it writes the start step and, when let go in the same pattern, ties the steps it was held across), `note(name, { duration, velocity })` (a short shot, used by the arpeggio), `bend(cents)` and `hit(row, velocity)` (a soft hit is recorded as a soft step). In `song-studio.js` ("playing live"): a press makes a *voice* (`{ el, stop() }`: held note, arpeggio member, strum, pad or roll); Hold keeps released voices in `pedal` until switched off; a touch waits 70 ms (or lifts) before playing so a swipe along the keys still scrolls; a mouse or pen sliding across keys plays each (glissando). The Play button opens `#studio-playpop` (absolute, above the keys) with the mode for the open track kind (Normal, Arpeggio, Strum, Random for notes; Normal, Roll for pads). Click events with no pointer (Enter, Space, a script's `.click()`) still play a single note or hit. **On a phone (640 px and under) the Tools sheet is a dropdown** under the Tools button (`placeSheet` sets `--sheet-top` and `--sheet-caret`; a tap outside closes it). `tests/e2e/test_studio_live.js` covers it.

Arrangement: `SongStudioHost.arr` (builder) is how the Studio edits bars: `info(track)`, `openBar`, `addBar`, `differ` (a bar gets a pattern of its own: a copy of that track's part only), `removeBar`, `setLoop`, `follow`, `setBars`. The builder has one open pattern at a time (the song's own `tracks` and `melody`), so opening a track or a bar opens the pattern that track plays in that bar. While playing, the Studio follows the music from bar to bar. Recording writes where the music is, not where it was scheduled: `recordingSpot(track)` uses the step that is sounding now and the pattern that track plays in this bar (another pattern's notes are written into `songData.patterns[X]`), and with Loop off on the open track (and no fixed length) `extendLaneForRecording` adds an empty bar just before the track runs out so the take can go on while the other tracks keep looping.

Things that have bitten: the studio's own buttons that only navigate or proxy undo/redo/play carry `data-no-history` (otherwise the click is captured as an edit, which would clear the redo stack or add a bogus undo step); `SVGElement` has no `hidden` property, use `toggleAttribute("hidden")`; the 24px floor rule for song controls on phones has an id in its selector, so studio sizes that need to be larger are repeated with `#song-builder-modal #song-studio` at the end of `style.css`; a row or roll that is hidden in the builder has no cells to click, so the studio opens it first; a rebuilt popover must give the focus back (otherwise Escape reaches the dialog and closes the whole builder); `.studio-pop` is shown and hidden by the class `is-open`, not `hidden`, so the volume slider can stay open on a wide screen. The builder tells the Studio about playback through `SongStudioHost` (the builder defines it) and `window.SongStudio.step/stopped/played/refresh/openLane`.

Pause is real: `createPlayer().start(atTime, { step, chainIndex })` carries on from a step, the builder remembers where it stopped (`resumeFrom`), and only the Studio's Pause sets it (the old Play still stops). The Studio's browser tests are `tests/e2e/test_studio_*.js` (page, desktop panels, playlist, roll, fold, live play, MIDI); the 18 older `test_song_*` browser tests drove the builder through the admin's song library, which is gone, and were deleted (re-creating them against `/studio` is on the outline). `tests/song-resume.test.mjs` and `tests/song-lanes.test.mjs` cover the logic.

## The look of buttons and fields

The default button is the chunky one: a thick ink outline, a flat fill and a hard shadow underneath that it sinks into when pressed. Fields are the same thick outline on a transparent fill, and `.field` (`<label class="field"><span class="field-label">…</span><input></label>`) puts the label in the outline like a legend. It is all tokens in `public/style.css` (`--btn-ink`, `--btn-fill`, `--btn-radius`, `--btn-border-width`, `--btn-shadow`, `--btn-shadow-sm`, `--field-border-width`, `--field-radius`; dark and light values), read by `.btn` (and `.btn-secondary`, `.btn-accent`), by a zero-specificity `:where(button, input…)` default (so a component that styles its own buttons keeps its look: nav tabs, chips, grid cells) and by the admin (`button` base rule and the chunky shadow list at the end of `admin/style.css`; the admin uses two pixels and the small shadow). The Bit bento look sets them on `body` (see "The redesign"). A new kind of button should use these tokens, not its own colours and radius.

## Dials, the picker menu and the nav

- **Dials:** `public/dial.js` (`window.Dial.enhance/scan`) turns every `input[type=range]` inside a `.dial-scope` (or `.dial-me`) into a rotary dial: an SVG face laid over the real input, which stays in the DOM, invisible, and keeps all its events, so nothing that reads or sets the range changes (setting `.value` from code redraws the dial; a MutationObserver picks up inputs added later). Drag up/down to turn, Shift = fine, double-click resets. The look is in the "Dials" block of `public/style.css` (`--dial-glow` is the pink arc). Today only the Studio (`#song-studio`) is a scope; new knob UIs should put `dial-scope` on their root instead of drawing their own. `.dial-input` has `!important` sizes on purpose: label rules like `.song-tempo-label input` would otherwise push the hidden input past a phone's width.
- **Picker menu:** the block picker (`#palette.is-picker-open`) is a rounded menu card (segmented Blocks / Page settings switch, one icon + label row per block, arrow keys move through the rows, Esc or the close button closes it).
- **Admin menus look like a browser's own menus** (the owner's pick for the admin and Site Settings): `--menu-bg`, `--menu-line`, `--menu-hover`, `--menu-shadow` near the end of `admin/style.css`, used by `.admin-more-panel` (Recent, notifications), `.size-menu`, `.studio-pop-menu`, the ☰ Tools groups and Site Settings (sections down the left from 900 px, each `.settings-group` a card with its title on top). Quiet rows, thin lines between groups; buttons pressed on purpose (bars, Save) stay chunky.
- **Block layout changes go through `block-fit.js`:** `fitWidth` (the Size menu: keep the left edge, grow right then left, never onto a neighbour) and `swapOrder` (the phone's ↑/↓: the two trade places, anything they now cover is pushed down), both covered by `tests/block-fit.test.mjs`. The canvas also redraws when its own width changes (a panel opening), not only on a window resize.
- **The nav is a camera dial:** each stop is an icon over a lowercase name (the label is stored as typed; `.tab-label` has `text-transform: lowercase`; `worker/nav-icons.js` picks the icon from the slug; unknown gets a dot), with a tick ruler along the bottom and a fixed needle with a glow in the middle (`.tab-indicator`, a sibling of `.tabs` inside `nav.site-nav` so it stays still while the strip scrolls). The stops are the fixed list `NAV_PAGES` plus the Settings button in `render.js`; there is no database-driven nav and no dropdown. **The strip is a dial you turn:** `.tabs` scrolls sideways with `scroll-snap-type: x mandatory`, every stop is the same width (`--stop-w` on `.site-nav`: 96px, 72px up to 720px wide) and there is padding of half the strip on both sides so any stop can come under the needle. The stop under the needle is the biggest and the others step down with their distance from it: `nav.js` writes each stop's distance in stops to `--d` as the strip moves and the CSS turns it into a scale, so the sizes follow the finger and need no animation. The lit stop is `.is-centred`. **The stop you are on is the one in the middle** (`place()` turns the dial to it, instantly on load and resize, gliding when the page changes, Settings while its dialog is open; a page with no tab rests on Home, unlit, with `.no-needle`). **Dragging the dial changes the page**: a scroll that is the visitor's (touch down, a sideways wheel, or the glide after a flick, told apart from the script's own turns and the browser's focus scrolls by `touching`, `userAt` and `progUntil`) calls `settle()`, and 160 ms after the dial stops on a stop that is not this page's, nav.js clicks it so page-slide takes it. A click on a stop turns the dial to it at once. Settings is a stop like the rest: pressing it toggles the dialog, and the dial settling on it opens it (`siteFinder.open({ focus })`); settling on a page's stop closes it again (setting `lastTarget` first so the dial is not turned back to the page it came from). Keyboard: Tab and the arrows turn the dial to the focused stop without going anywhere until Enter; focus that comes back by itself (the dialog closing) must not move the dial, and a glide is started a tick late (`centreOn`) because the browser scrolls a just-focused stop into view and would cut it short. `centreOn` is the only place that scrolls the strip. **The middle stop is exactly in the middle by the layout itself:** the padding either side of the stops is `50% - stop/2`, so a stop at a whole number of steps is at 50% of the strip whatever its width, and the needle is `left: 50%`; keep stops an even width. **A page also centres the dial before its first paint:** `DIAL_PRESET_SCRIPT` (`worker/nav-dial-script.js`) is an inline script right after the nav that scrolls to this page's stop and sets every `--d`, so on a slow connection the dial is not left at its first stop until `/nav.js` arrives (`test_nav_dial.js` delays nav.js to check); change the dial's maths in both places. Never put a wrapper between `.tabs` and the stops: nav.js, page-slide and the tests select `:scope > .tab`. `tests/e2e/test_nav_dial.js` (real touch drags through CDP, hold still before letting go or the flick carries it past the stop) covers it. The header is only the dial, centred, and it is the same height on every page, the Studio included (the bar must not jump between tabs, `test_nav_carousel.js` checks it). **The ruler under the tabs is drawn by `nav.js` (`ruler`) from the stops:** a `.tab-ruler` of `<i>` marks inside the strip (so it scrolls with the tabs), a long tick under the middle of every stop and five short ones evenly between neighbours, carried on to both ends, each on a whole device pixel. A repeating background was tried twice and drifted, so do not go back to one.
- **Tabs slide in place:** `page-slide.js` swaps the content like a carousel for every nav page, including the Studio (its scripts are loaded once, `LOADABLE`, and set up per page through `window.siteInitContent` → `siteInitApps`). It fires `site:leave` before a swap and `site:arrive` (with `detail.old`, the outgoing page) just before the old page is removed. A tag a script adds to `<head>` must carry `data-added-by`, or the head no longer matches the other pages and every tab after it is a full load. Every nav page is fetched in the background once the page has settled, and a fetched page is kept for the whole visit: a tap shows the copy it has at once and fetches a fresh one in the background when the copy is over 30 s old (`fetchDoc`, stale-while-revalidate). A mouse drag does the same as a touch swipe (`mousedown`/`mousemove`, `startSwipe`/`moveSwipe`/`endSwipe`): it starts only on the page's own space, after a sideways pull of 28 px with nothing selected, swallows the click that ends it; App pages (`.app-native`) stay out of it. Live-site rules (`whyNot`): scripts under `/cdn-cgi/` and from other sites never force a full load, and `revealEmails` puts back the addresses Cloudflare's email protection hides. A slide that still falls back logs why (console and `sessionStorage.slideFallback`). `tests/e2e/test_nav_carousel.js` and `test_mouse_swipe.js` cover it.
- **Visitor songs on /studio** are saved on their first change (`keepDrafts` in `studio.js`), since the builder only autosaves a song that has been saved once.

- **The builder's markup is `public/studio/dialogs.txt` and its styles are `public/studio/studio.css`**, both fetched once by the kit. ## The app kit (the Studio's shell)

`public/app-kit.js` (`window.SiteAppKit`) with `public/app-kit.css` is the shell the Studio is built on (it used to carry four more apps; they are gone, so it is smaller than the older notes in this file suggest).
- **What it does:** fetches `/studio/dialogs.txt` and `/studio/studio.css` once (plus `app-kit.css`) and puts the styles in one `<style id="app-kit-css" data-added-by>`, takes the Studio's dialogs out of the dialogs file, preloads all the scripts at once and runs them one after another in order, and `register(app)` runs the page life (boot on the mount, park in `#app-parking` on `site:arrive`, place back on return, `window.siteInitApps` called from `siteInitContent`). On the other pages it fetches nothing until someone points at, touches or tabs to the studio stop (`warm`). The editor's calls to the old admin API are answered in the browser: `addApi(fn(path, method, body, query))` (return `undefined` for a path that is not yours). Nothing is sent to the server.
- **What it exports:** `esc, fail, addApi, readList, writeList, nextId, now, cleanName, whenEdited, backup, register`. `openStart()` and `wideQuery` still work: the Studio opens straight into an empty song, and its Songs panel appears from 1280 px.
- **Style rule:** `studio.css` is plain CSS with `.app-native` in front of every selector (`body` became `.app-shell`, `:root` rules keep their place). It is no longer scoped in the browser, so there is no run-time re-serialising to trip over, but a new rule must carry the scope itself or it will leak into the rest of the site.
- **Backup of browser-kept data:** `public/backup-logic.js` (`window.BackupLogic`, pure, `tests/backup-logic.test.mjs`) makes and reads a `dominick-backup` v1 file; merging never overwrites (duplicates skipped, new ids for clashes). The Studio shows the buttons through `K.backup(cfg)`. `tests/e2e/test_backup.js`.
- **Phone calm (`@media (max-width: 640px)` at the end of `app-kit.css`):** scoped `.app-native` so the owner's admin and the desktop stay as they are. Add new phone spacing there, not in the admin stylesheet.
- **MIDI tab (Studio Tools):** the builder owns the Web MIDI connection (`connectMidi`, `SongStudioHost.midi`: `info`, `connect`, `refresh`, `subscribe`, `canRecord`); `buildMidiPane` in `song-studio.js` is only the view. `tests/e2e/test_studio_midi.js` fakes `navigator.requestMIDIAccess`.

## The study modules

Two password-protected study pages, the A+ Core 1 drill and the WGU C777 web development drill, open in a full-screen popup from **Study blocks on the home page**. Read `worker/study/README.md` first: it covers how the block works, the password (every block asks; the block's own, else the Worker's `STUDY_PASSWORD` secret, else a built-in default that keeps casual visitors out and nothing more), where progress and weak spots are kept (the visitor's browser), how to add a lab, and how to take it all out. ## The home page

One D1 page, slug `home`, rendered by `renderHome` in `worker/index.js` from its blocks (`renderBlocks` in `render.js`). Block types: heading, text, image, button, divider, spacer, quote, gallery, study. Text blocks take minimal markdown (`paragraphsHtml`: paragraphs, `##`/`###` headings, lists, quotes, code, **bold**, *italic*, links). A block of any other type already in the database renders nothing. There is no navigation to other pages: the nav is fixed (studio, home, settings).

## Recipes

- **New admin API route:** add an `if (path === "/thing" && method === …)` block in `routeAdminApi` (use `readJsonBody`, `json`, and `log(ctx, env, "create", "thing", name)` for the activity log if `log` still writes one), keep it behind the router's auth gate, and add a line to `scripts/smoke.mjs` if a visitor must be refused.
- **New admin tool/dialog:** markup in `index.html` (sidebar button in a `.admin-sidebar-group`, modal near the others, script tags at the end), logic in `app.js` or its own `public/admin/<name>.js`, CSS appended to `public/admin/style.css` using existing tokens (`--bg`, `--bg-elevated`, `--border`, `--text-dim`, `--accent`, `--error-text`, `--success`, `--warning`), a command-palette entry (grep `Open Backups`), a sidebar icon (`#<id> { --ico: … }`).
- **New stored list:** settings rows (rule 2) with their own route (cap the count and the size; validate in a small pure file).
- **New block type / song feature:** find the nearest existing one (`grep -n` for a sibling such as `quote`, `ties`) and follow it end to end: validation → admin UI → public render → CSS → tests.
- **New dead-code check:** the `worker/` modules form one import graph from `index.js`; a function nothing reaches is dead. A short parser script that walks it is the way to find them (do not trust text search alone), but keep what only a test uses on purpose (see Testing).

## The board (features.json)

The admin's Features board is a read-only kanban: **To do** on the left, **Working on now** and **Done** on the right. It is driven by `features.json`: `{"id", "area", "status", "kind", "title", "summary", "notes", "date"}` and a bumped `updated`. Status is `todo`, `doing`, `done` or `parked`; an open item needs a `kind`: `decision` (waiting on the owner: `notes` must say what to decide), `bug`, `attention`, `almost` or `idea`. Plain language, no internal item numbers. `node tests/run.mjs features` checks the file.

**The loop:** pick something from `todo` (waiting-on-owner items can't be picked), set it `doing` and push so the owner sees it move; do the work; set it `done` with `"date": "<today>"` in the same commit as the work; pick the next. Keep two or three `doing` at most. New things you build that were never on the board get a `done` entry too. (The old "owner's own requests" form on the live site was removed with the rest of the cut; the board is edited in `features.json` only.)

## Working with the owner

Casual, direct, short. Ask when the request is vague instead of guessing. Push back lightly when something doesn't add up. Make a recommendation instead of listing every option. Ask before anything hard to reverse or outward-facing.
