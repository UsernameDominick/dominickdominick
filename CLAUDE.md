# dominickdominick.com — notes for Claude

A personal site on a Cloudflare Worker + D1 (database) + R2 (media), with a built-in visual page editor, articles, projects, a circuit
simulator, a song builder, 3D scans and a photo editor. The owner is the only admin. `README.md` is the user-facing description;
this file is what you need to work here quickly.

## Where things are

| Path | What it is |

## Run it

```bash
npx wrangler dev --port 8787        # local site at http://localhost:8787, admin at /admin
npx wrangler d1 execute DB --local --command "select …"   # poke the local database
```
`.dev.vars` holds `ADMIN_PASSWORD` and `SESSION_SECRET` (gitignored). Never print them or paste them anywhere.
Static files in `public/` are served straight from disk, so a browser reload picks them up; Worker code reloads by itself.

## Testing (do this before every commit)

```bash
node tests/run.mjs                    # all pure tests, ~6 s. `node tests/run.mjs song sim` filters by name.
node tests/e2e/run.mjs                # all browser tests, parallel. `node tests/e2e/run.mjs prepublish` filters by name.
node tests/e2e/run.mjs --live test_x  # one test against the dev server already running on :8787 (fast, but changes that database)
```
- The e2e runner starts its own throwaway servers on copies of the local D1/R2, so tests may create and delete freely and the dev
  database is untouched. It prints only **new** failures: tests that already failed are in `tests/e2e/known-failing.txt`
  (fix one, delete its line). A test that fails under load is retried once on its own and reported as "Flaky" if it then passes (`--no-retry` turns that off; keep it
  in mind when a test only fails in the full run). First time on a machine: `cd tests/e2e && npm install` (Playwright + axe-core).
- **Don't edit `worker/` or `public/` while a test run is going** (the servers reload mid-test and make false failures).
- A new feature gets a node test (`tests/<name>.test.mjs`, must print `ALL PASS`; copy the style of a neighbour) for its pure logic,
  and a browser test (`tests/e2e/test_<name>.js`, copy a neighbour: it uses `E2E_BASE` and `ADMIN_STATE`) for the UI.
- Three by-hand audits (not tests, run them after a UI change and read the report): `node tests/e2e/audit/audit-apps.js` (the four app pages on a phone and a computer, dark and light, shelf and editor open: overflow, off-screen parts, the editor under the nav, axe, controls under 24 px; `--only Scans` for one), `node tests/e2e/audit/audit-public.js` (every public page: SEO, axe, overflow, links, weight) and
  `node tests/e2e/audit/audit-admin.js` (every admin tool, its tabs and editors, dialogs and dropdowns: axe, overflow, tap targets, focus, Esc; `--only articles-btn` for one tool).
  All three need `wrangler dev` running on :8787 and only open and close things. Expect 0 high / 0 medium; the admin one cannot reach the CDN or GitHub in a sandbox, which it ignores, and its "focus went to BODY" lows are the audit opening tools from a menu that is hidden (real clicks and Esc return focus correctly).
- A browser test that adds an admin dialog should also run axe (see `test_scripts_e2e.js`) in dark and light, and check a 390 px width.
- Test data is synthetic (prefix titles with `QQ`). If you must use `--live`, clean up what you made.
- Before saying a failure is "not mine": check it on the previous commit (`git stash`/checkout, run that one test, restore).

## Rules that have bitten before

1. **D1 allows 100 bound variables per statement.** Chunk big `IN (…)` lists (`chunkList`, `selectIn`, `updateIn` in `db.js`, 90 per chunk).
2. **Settings rows are the schema-free store.** Lists of small things live in the `settings` table under a prefix (`page_section:<id>`,
   `admin_script:<id>`), one row each, so no migration is needed and backups (`exportAll` dumps every settings row) include them.
3. **Anything that animates in the public CSS must sit inside `@media (prefers-reduced-motion: no-preference)`** (`tests/reduced-motion.test.mjs` fails otherwise).
4. **The CSP has no `unsafe-eval`.** No `eval`/`new Function` anywhere in browser code; code that must run is loaded as script text/blob (see `script-runner.js`).
5. **Circuit simulation is mirrored by hand:** `public/admin/sim-components.js` (builder) and `worker/simulation-render.js` (public page) must
   agree, with `sim-solver.js` and `sim-schematic.js` shared. Change one, change the other, and the `*-parity.test.mjs` files must pass. New resistive parts reuse the edge kind `"resistor"` with a flag.
6. **Audio plays only after a click** (`public/sim-buzzer.js` is the shared tone module). Never autoplay.
7. **A new file that public visitors need while the site is in maintenance mode** goes in `MAINTENANCE_EXEMPT_FILES` in `worker/index.js`.
8. **Every admin dialog** is a `.modal` with `role="dialog"`, a `close-…` button (Esc and backdrop click press it), and is added to the Ctrl+S map near
   "Keyboard shortcuts" in `app.js` if it has a Save. Dialog stacking and focus return are handled for you (`modalFocusReturn`).
9. **Saves that can race** use `expected_version` (`checkConflict`). Autosave must never publish a draft by itself.
10. **Text from users or from scripts is data.** Escape with `escapeHtml` in admin templates; the public side goes through `worker/text.js` / `render.js` helpers.
11. **Server validation in a small pure file, then called from the route** (see `worker/redirects.js`): keeps it testable and keeps `admin-api.js` readable.
12. Page and article bodies need > 50 characters before they can be published (server check) — tests that publish need a real-length body.
13. **No emoji anywhere on the site** (the owner's rule, public and admin, and in `outline.md` / `features.json`). That includes symbols phones draw as
    emoji (play ▶, pause, stop, record, the north-east arrow, warning sign): use words, or a drawn icon from `worker/ui-icons.js` (`uiIcon(name)`;
    `.ui-icon` in `public/style.css`). Plain text marks (✓ × ← → ♪ ©) are fine. `tests/no-emoji.test.mjs` fails on any, escapes included; a line
    that only holds one as data (the stored reaction keys) is marked `// no-emoji: data` and uses an escape.

## Songs: how a song is stored

A song is one JSON blob (`songs.data`). The sound is made by `public/song-engine.js` (shared by the admin builder, the public embed and the offline renders), the editor is `public/admin/song-builder.js`, and `public/admin/song-files.js` is the pure helper for MIDI, JSON import/export and import cleaning.
- **A new song field has to be added in four places or it silently disappears:** the engine (`scheduleStep` or a send like `setSpace`), `worker/songs.js` (`songDataError`, validation), `song-files.js` (`cleanSong`, or import drops it), and `song-builder.js` (open, undo restore in `applySongHistoryState`, the control). Add the field to `tests/song-files.test.mjs`'s "exactly the builder's own keys" list only if it is written for every song; optional fields (voice, patterns, chain, editing) are written only when set, so old songs and their noise seed stay identical (`tests/song-chain.test.mjs` pins the seed values).
- **Patterns:** the pattern being edited is always the song's own `tracks`, `melody.notes` and `melody.ties` (every editing tool works on it unchanged); `editing` names it (absent = "A") and `patterns` holds the others as `{tracks, notes, ties}`; `chain` is the song order (up to 32 letters). Mix, instrument, scale, tempo, echo and the rows themselves (`trackMeta`) are shared. Resolve patterns only through the engine's `patternData` / `chainOf` / `viewOf` (and `chainParts` in song-files.js, kept equal by a test), never by reading `songData.tracks` for "the song".
- **Extra melodic parts (bass, chords, lead):** `bass`, `chords` and `lead` are each `{notes, ties, voice, volume, muted, hidden}` with the same shape as `melody`, over a two-octave roll of their own (bass C1 to B2, chords C3 to B4, lead C4 to B5; melody is C3 to B4), with default voices bass, pad and lead. The engine keeps them in one registry (`PART_KEYS`, `PART_NOTES`, `PART_OCTAVES`, `partVoiceOf`, `isPartMuted`); `worker/songs.js` and `song-files.js` loop the same keys, so a fourth part is a one-line addition in each. A part is absent until used (the builder creates it in memory with `ensurePart(key)` and `pruneParts()` drops an empty, uncustomised one at save, so old songs are stored unchanged and the engine's noise seed only includes parts that have notes). The open pattern's part is `songData[key].notes/ties`, every other pattern's is `patterns[X][key] = {notes, ties}`, and it follows the same four-places rule. In the builder the piano roll shows one part at a time (`rollPart`, `roll()`, `rollNotes()`), so every roll tool works on any of them; never read `songData.melody` in code that should also serve the other parts. A MIDI file writes bass, chords and lead on channels 2 to 4 (own tracks named Bass, Chords, Lead; the chords and lead tracks carry a marker text event so our own file re-imports into the right part); a foreign track named "bass" or one mostly below C3 becomes the bass.
- **Bars, lanes, sound tweaks:** `bars` (1 to 64, absent = as long as the music) is the song's length; `lanes` is `{ drums|bass|chords|melody|lead: { order: ["A","B"], loop: false } }`, a run of patterns for one track (a track with no lane follows the song order `chain`; a lane shorter than the song loops until it ends unless `loop` is false). There are 16 patterns (A to P) and the order is at most 64 bars. The engine resolves it with `songBars` / `laneOrder` / `patternAtBar` / `barView` (the song as it sounds in one bar; `viewOf` when there are no lanes), the player reports `info.patterns` (the pattern each track plays now) and `currentPatternFor(track)`, and `song-files.js` `chainParts` is kept equal by `tests/song-chain.test.mjs` and `tests/song-lanes.test.mjs`. A part (and melody) can carry `synth`, a few clamped tweaks laid over its named voice (`Engine.cleanSynth`; the same ranges are in `song-files.js`, and `worker/songs.js` only checks the keys and types). `scale` may carry `snap: true` (notes played or tapped move to the scale). The defaults for a new song come from Site Settings (`song_default_tempo/bars/kit`, `worker/song-defaults.js`).
- **Sounds:** the instruments are `MELODY_VOICES` in the engine (grouped for the menus by `VOICE_GROUPS`; the builder fills `#song-voice`, `#song-bass-voice`, `#song-part-voice` and `#song-kit` from the engine at start, so a new voice or kit is added in the engine, in `song-files.js` (`MELODY_VOICES`, `KITS`; a test keeps them equal) and, for a kit, in `worker/song-defaults.js` and the Settings menu in `index.html`; the first five voices and three kits are pinned, their numbers never change). Kits are `KIT_PARAMS` over `DEFAULT_KIT` (a kit only names what differs; `KITS` is the menu order because number-like names sort first in an object). A voice may use `unison`, `sub`, `partial`, `noise`, `drive`, `fm`, `tremolo`, `vibrato`, `wobble`, `slide`, `ftype` and a filter sweep; these parts are only built when asked for. A track's `synth` tweaks (`SYNTH_RANGES` + `ftype`) are mirrored in `song-files.js` and `worker/songs.js` (`SYNTH_KEYS`). One drum sound's own `tune`, `decay` and `tone` live in `trackMeta[row]` (`DRUM_RANGES`, `drumShape`, `kitParams`; mirrored in `song-files.js` and checked in `worker/songs.js`). A new knob is added in all of those and in the Studio's `KNOBS`.
- **Audio wakes from a tap:** a phone keeps the sound asleep, so everything that makes a sound calls the builder's `ensureAudio()` first (Play, Preview, keys, pads). Do not add a new sound path that calls `getAudioCtx()` alone.
- **Recording helpers:** `quantizeSteps` (0, 1, 2 or 4; `localStorage.songQuantize`) moves a recorded note to the nearest grid line in `recordingSpot`; the Studio keeps `followOn` (`songFollow`) and `recTop` (`songRecTop`: arming Rec, or Play while armed, starts from the top).
- **Pump** (`pump`, 0 to 100, absent when off) ducks all the music (melody, bass, chords, lead) on every kick: with it on, `scheduleStep` routes `scheduleMusic` through a per-context music bus (`withMusicBus`) that `duckMusic` automates. With it off nothing extra is built, so graphs and seeds are unchanged (`tests/song-pump.test.mjs`).
- Drum rows: the four core rows always exist; open hat, rim, tom and crash exist once added (found by their `trackMeta` entry). Melody instruments are `melody.voice` (absent = the plain waveform note).
- Test helpers: `tests/fake-audio.mjs` (recording Web Audio stand-in plus engine and song-files loaders). A browser test can see which pattern is sounding by wrapping `SongEngine.createPlayer` in an init script (see `tests/e2e/test_song_patterns.js`).

## Song Studio view

`public/admin/song-studio.js` is the Song builder's only UI, built for a phone first. Top to bottom: the five tracks (on a phone or tablet one row of tabs, the open one wider, a dot on a track that has notes; swipe across or tap; on a screen 1024 px and up a rail of five cards on the left with a preview of each), the open track (one row of controls: its bars, + Bar, Loop, Steps or Roll, the sound named on its button, Mute, Clear and a ⋯ menu with Track tools, the bar actions and the song length; on a phone Loop, Mute, Clear and MIDI move into that menu), the steps or roll filling what is left (the only part that scrolls; a phone shows half a bar of steps at a time with a "Steps 1–8 / 9–16" pager and snap scrolling, and opens note tracks in the Roll), the transport (Play, Stop, Undo, Redo on a wider screen, the Rec hub with its fan, BPM), and the keys or pads at the bottom. A phone on its side puts the transport and keys in a column on the right. The track counts are what each track plays in the bar picked for it (`cardInfo`), not the open pattern. **Tools** (top bar) opens a sheet with five tabs: Sound (the open track's instrument, a Wave and sliders for attack, decay, sustain, release, brightness, thickness and vibrato; for Drums the kit, one chosen sound's volume and mute, add a sound), Track (the builder's own tools for the open track and the scale with Snap), Song (tempo, length, swing and the rest, metronome sound, mix, notes, templates), Patterns (the builder's arrangement section) and Share (player look, preview, exports). There is no other view: `localStorage.songView = "classic"` still shows the old editor, but only so the older browser tests (which the runner seeds with it) keep driving it; nothing offers it.

It stores nothing and is a view over the builder's own editor, which stays in the page, hidden. **The five tracks are fixed and in this order, 1 Drums, 2 Bass, 3 Chords, 4 Melody, 5 Lead** (the owner asked for a set order that cannot be changed or extended; do not add a way to add, remove or reorder them); each is also the name of its lane. They are a grouping of the song's own data: Drums is every drum row in one grid (with pads for keys), the others are the `bass`, `chords`, `melody` and `lead` parts, each on its own roll. The step cells are a mirror painted from `songData`, and every control drives the builder's: a tap clicks the matching step (`#song-sequencer` / `#song-piano-roll`), choosing a note track clicks the `#song-roll-<part>` button so the real roll shows that part, sliders and menus set the matching control and fire its event, play is `#song-play`. The sheet **moves the builder's own controls into it, ids and all** (`buildSheet`), so they keep working; the selects the Sound tab drives (`#song-voice`, `#song-bass-voice`, `#song-part-voice`, `#song-kit`, `#song-waveform`) stay hidden in the builder. A card counts a held (tied) step as part of the note before it, not as another note. The Roll draws by dragging (`host.group(true/false)` makes the whole drag one undo step).

Arrangement: `SongStudioHost.arr` (builder) is how the Studio edits bars: `info(track)`, `openBar`, `addBar`, `differ` (a bar gets a pattern of its own: a copy of that track's part only), `removeBar`, `setLoop`, `follow`, `setBars`. The builder has one open pattern at a time (the song's own `tracks` and `melody`), so opening a track or a bar opens the pattern that track plays in that bar. While playing, the Studio follows the music from bar to bar. Recording writes where the music is, not where it was scheduled: `recordingSpot(track)` uses the step that is sounding now and the pattern that track plays in this bar (another pattern's notes are written into `songData.patterns[X]`), and with Loop off on the open track (and no fixed length) `extendLaneForRecording` adds an empty bar just before the track runs out so the take can go on while the other tracks keep looping.

Things that have bitten: the studio's own buttons that only navigate or proxy undo/redo/play carry `data-no-history` (otherwise the click is captured as an edit, which would clear the redo stack or add a bogus undo step); `SVGElement` has no `hidden` property, use `toggleAttribute("hidden")`; the 24px floor rule for song controls on phones has an id in its selector, so studio sizes that need to be larger are repeated with `#song-builder-modal #song-studio` at the end of `style.css`; a row or roll that is hidden in the builder has no cells to click, so the studio opens it first; a rebuilt popover must give the focus back (otherwise Escape reaches the dialog and closes the whole builder); `.studio-pop` is shown and hidden by the class `is-open`, not `hidden`, so the volume slider can stay open on a wide screen. The builder tells the Studio about playback through `SongStudioHost` (the builder defines it) and `window.SongStudio.step/stopped/played/refresh/openLane`.

Pause is real: `createPlayer().start(atTime, { step, chainIndex })` carries on from a step, the builder remembers where it stopped (`resumeFrom`), and only the Studio's Pause sets it (the old Play still stops). `tests/e2e/test_song_studio.js` switches to the Studio itself (desktop, bars and free recording, a 390 px touch phone, hidden rows, the Songs settings tab; `test_song_parts.js` covers the Chords and Lead parts in the old editor), and `tests/song-resume.test.mjs`, `tests/song-lanes.test.mjs` and `tests/song-defaults.test.mjs` cover the logic.

## The look of buttons and fields

The default button is the chunky one: a thick ink outline, a flat fill and a hard shadow underneath that it sinks into when pressed. Fields are the same thick outline on a transparent fill, and `.field` (`<label class="field"><span class="field-label">…</span><input></label>`) puts the label in the outline like a legend. It is all tokens in `public/style.css` (`--btn-ink`, `--btn-fill`, `--btn-radius`, `--btn-border-width`, `--btn-shadow`, `--btn-shadow-sm`, `--field-border-width`, `--field-radius`; dark and light values), read by `.btn` (and `.btn-secondary`, `.btn-accent`), by a zero-specificity `:where(button, input…)` default (so a component that styles its own buttons keeps its look: nav tabs, chips, grid cells) and by the admin (`button` base rule and the chunky shadow list at the end of `admin/style.css`; the admin uses two pixels and the small shadow). Site Settings > Buttons & controls changes them through `CONTROL_PRESETS` (worker/render.js, mirrored in `ADMIN_CONTROL_PRESETS` in app.js and the buttons in index.html): the new default of each group is `chunky`, the old looks are still there. A new kind of button should use these tokens, not its own colours and radius.

## Dials, the picker menu and the Studio fan

- **Dials:** `public/dial.js` (`window.Dial.enhance/scan`) turns every `input[type=range]` inside a `.dial-scope` (or `.dial-me`) into a rotary dial: an SVG face laid over the real input, which stays in the DOM, invisible, and keeps all its events, so nothing that reads or sets the range changes (setting `.value` from code redraws the dial; a MutationObserver picks up inputs added later). Drag up/down to turn, Shift = fine, double-click resets. The look is in the "Dials" block of `public/style.css` (`--dial-glow` is the pink arc). Today only the Studio (`#song-studio`) is a scope; new knob UIs should put `dial-scope` on their root instead of drawing their own. `.dial-input` has `!important` sizes on purpose: label rules like `.song-tempo-label input` would otherwise push the hidden input past a phone's width.
- **Picker menu:** the block picker (`#palette.is-picker-open`) is a rounded menu card (segmented Blocks / Page settings switch, one icon + label row per block, arrow keys move through the rows, Esc or the close button closes it).
- **Studio ⋯ row:** the hub's big button is Rec: a tap records, a hold (420 ms) or the ⋯ button opens `#studio-fan`, a row of nine pastel icon buttons laid over the transport bar (it fills the bar, so nothing above is covered; no labels, the owner asked for just the buttons): volume, metronome, undo, redo, stop, clear, start-from-top, quantize, follow, then × (`#studio-fan-close`). Stop/Undo/Redo are also on the bar as `#studio-stop`, `#studio-undo`, `#studio-redo`; the row's own are `#studio-fan-stop/undo/redo/clear`. Volume and metronome open a small popover above the row. Quantize shows its setting (`#studio-quant-value`: 1/16, 1/8, 1/4, Off) and a tap moves to the next (`QUANT` in `song-studio.js`; triplets would need a triplet grid, the steps are sixteenths). While the row is open it covers Play and Rec, so tests close it (`#studio-fan-close`) before pressing those. Tests that press a row control go through `tests/e2e/_fan.cjs` (`fanify(page)`), which opens the row first.
- **The nav is a camera dial:** each link is an icon over a lowercase name (the label is stored as typed; `.tab-label` has `text-transform: lowercase`; `worker/nav-icons.js` picks the icon from the slug or label; unknown gets a dot), with a tick ruler along the bottom and a fixed needle with a glow in the middle (`.tab-indicator`, a sibling of `.tabs` inside `nav.site-nav` so it stays still while the strip scrolls). **The strip is a dial you turn:** `.tabs` scrolls sideways with `scroll-snap-type: x mandatory`, every stop is the same width (`--stop-w` on `.site-nav`: 96px, 72px up to 720px wide) and there is padding of half the strip on both sides so any stop, first or last, can come under the needle. The stop under the needle is the biggest and the others step down with their distance from it: `nav.js` writes each stop's distance in stops to `--d` as the strip moves and the CSS turns it into a scale (icon `1 - 0.2*min(d,2.5)`, name a little less, name opacity), so the sizes follow the finger and need no animation (reduced motion needs nothing special). The lit stop is `.is-centred` (before nav.js has run, `.tabs:not(.dial-ready) .tab.is-active`). **The stop you are on is the one in the middle** (`place()` turns the dial to it, instantly on load and resize, gliding when the page changes, Search while the finder is open; a page with no tab rests on Home, unlit, with `.no-needle`). **Dragging the dial changes the page**: a scroll that is the visitor's (touch down, a sideways wheel, or the glide after a flick, told apart from the script's own turns and the browser's focus scrolls by `touching`, `userAt` and `progUntil`) calls `settle()`, and 160 ms after the dial stops on a stop that is not this page's, nav.js clicks it so page-slide takes it. A click on a stop turns the dial to it at once. Search is a stop like the rest but is only opened by pressing it (`settle()` skips buttons). Keyboard: Tab and the arrows turn the dial to the focused stop without going anywhere until Enter; focus that comes back by itself (the finder closing) must not move the dial, and a glide is started a tick late (`centreOn`) because the browser scrolls a just-focused stop into view and would cut it short. `centreOn` is the only place that scrolls the strip. **The middle stop is exactly in the middle by the layout itself:** the padding either side of the stops is `50% - stop/2`, so a stop at a whole number of steps is at 50% of the strip whatever its width (a scrollbar coming or going, a panel opening, an odd viewport), and the needle is `left: 50%`; keep stops an even width. **A page also centres the dial before its first paint:** `DIAL_PRESET_SCRIPT` (`worker/nav-dial-script.js`) is an inline script right after the nav that scrolls to this page's stop and sets every `--d`, so on a slow connection the dial is not left at its first stop until `/nav.js` arrives (`test_nav_dial.js` delays nav.js to check); change the dial's maths in both places. `centreHome` in `worker/nav-order.js` orders the stops with Home in the middle, the others split either side, Search last (so on the home page Home is under the needle with stops on both sides); `finderHtml` keeps the data order. The simulations stop is called **Sim** (`BUILTIN_NAV`), and names are lowercase by CSS only (`.tab-label` has `text-transform: lowercase`; the label is stored as typed). Never put a wrapper between `.tabs` and the stops: nav.js, page-slide and the tests select `:scope > .tab, :scope > .tab-group`. `tests/nav-order.test.mjs` and `tests/e2e/test_nav_dial.js` (real touch drags through CDP, hold still before letting go or the flick carries it past the stop) cover it. The header is only the dial, centred (the owner took the site name off it; `site_brand` is still the name in titles and feeds), and it is the same height on every page, the Studio included (no page-specific header sizes: the bar must not jump between tabs, `test_nav_carousel.js` checks it); the dial's last stop is **Search** (`#finder-open`), which opens **the finder** (`#site-finder`, built by `finderHtml` in `render.js`, driven by `nav.js`; it opens under the nav, which stays in view and can be pressed: `--finder-top` is where the header ends, Search lights up and toggles it, another tab closes it): one box like a Mac's Spotlight that searches the site as you type (`/api/search-suggest`), finds the site's settings (the old `#theme-toggle`, `#motion-toggle`, `#font-size-toggle` buttons live in it as rows), the nav sections, Surprise me, Saved, History and the owner's Edit this page. `/` or Ctrl/Cmd+K opens it, arrows move, Enter opens the top hit (a setting or section whose name starts with what was typed) or searches the site, Esc closes and returns the focus.
- **Admin menus look like a browser's own menus** (the owner's pick for the admin and Site Settings): `--menu-bg`, `--menu-line`, `--menu-hover`, `--menu-shadow` near the end of `admin/style.css`, used by `.admin-more-panel` (Recent, notifications), `.size-menu`, `.studio-pop-menu`, the ☰ Tools groups and Site Settings (sections down the left from 900 px, each `.settings-group` a card with its title on top). Quiet rows, thin lines between groups; buttons pressed on purpose (bars, Save) stay chunky.
- **Block layout changes go through `block-fit.js`:** `fitWidth` (the Size menu: keep the left edge, grow right then left, never onto a neighbour) and `swapOrder` (the phone's ↑/↓: the two trade places, anything they now cover is pushed down), both covered by `tests/block-fit.test.mjs`. The canvas also redraws when its own width changes (a panel opening), not only on a window resize.
- **What the nav leaves out (owner's choice: a bar of just Home, Studio and Search):** the built-in Articles (`/random`), Projects and Topics links are out by default (`hiddenByDefault` in `worker/nav-settings.js` and `BUILTIN_NAV_LINKS` in app.js, `builtinHidden`; Site Settings > Header & footer can switch one back on, stored as `{"projects":{"hidden":false}}`), and a page of the owner's own on one of those addresses follows the same switch; the finder offers "All articles" instead. On a phone the dial spans the bar (the dial is at most 760px wide on a bigger screen) and shows about five stops at a time. **The ruler under the tabs is drawn by `nav.js` (`ruler`) from the stops, in every mode:** a `.tab-ruler` of `<i>` marks inside the strip (so it scrolls with the tabs), a long tick under the middle of every stop's link (the link, not the caret, of a stop with a dropdown) and five short ones evenly between neighbours, carried on to both ends, each on a whole device pixel. A repeating background was tried twice and drifted (its tiles never matched the tabs' widths, it did not follow the scrolling, and Safari rounds every tile), so do not go back to one. The stops, the marks and the middle are measured in the same coordinates (from the left edge of the strip's scrolled content), so the needle always lands on a tick when the dial rests on a stop. A page with no tab of its own (a missing page, an article) keeps the ruler and has no needle (`place` sets `.no-needle`, which hides the indicator, so no stub is left at the edge). `tests/e2e/test_nav_carousel.js` checks ticks, needle (in the middle, on the current stop's tick) and short-tick spacing at five widths and densities, after every tab and after scrolling. Hidden Notes is never a tab: the signed-in owner finds it in the finder (`nav.owner`). A page holding a Study block is out of the nav, the sitemap and search engines (`listStudyPageIds`, noindex), is found through the site's search, and every Study block asks for its password (the old tick no longer matters, `gatePassword`).
- **Tabs slide in place:** `page-slide.js` swaps the content like a carousel for every nav page, including ones with the song and circuit players (their scripts are loaded once, `LOADABLE`, and set up per page through `window.siteInitContent` → `siteInitSongs` / `siteInitSims` / `siteInitApps`; a playing song stops on the way out) and the app pages (Studio, PicEditor, Simulations, Scans). It fires `site:leave` before a swap and `site:arrive` (with `detail.old`, the outgoing page) just before the old page is removed. A tag a script adds to `<head>` must carry `data-added-by`, or the head no longer matches the other pages and every tab after it is a full load. Every nav page is fetched in the background once the page has settled (and again after each slide), and a fetched page is kept for the whole visit: a tap shows the copy it has at once and fetches a fresh one in the background when the copy is over 30 s old (`fetchDoc`, stale-while-revalidate). A nav page that holds an app (Studio, PicEditor, Simulations, Scans) also gets `/app-kit.js` and the app's script loaded early, which on another page only fetches the editor's markup and styles and prefetches the app's scripts while the browser is idle (`warm`), so that tab opens without waiting. `tests/e2e/test_nav_carousel.js` covers it. **Like a carousel:** the strip travels past the pages in between (`pagesBetween`, ghosts drawn from the fetched copies with their ids stripped, `ghostOf`), farther tabs take a little longer; on a touch screen a sideways swipe on the page moves to the tab beside it, following the finger (`startSwipe`/`moveSwipe`/`endSwipe`; not on anything listed in `SWIPE_OFF` (which includes every app page's `.app-native`) or that scrolls sideways, not within 24 px of the screen edges). **Live-site rules (`whyNot`):** scripts under `/cdn-cgi/` and from other sites (Cloudflare's email protection and analytics) never force a full load, and `revealEmails` puts back the addresses Cloudflare's email protection hides; a page's own head styles are swapped in and out (`swapStyles`) instead of forcing a full load. A slide that still falls back logs why (console and `sessionStorage.slideFallback`). `test_nav_carousel.js` fakes those Cloudflare additions.
- **Visitor songs on /studio** are saved on their first change (`keepDrafts` in `studio.js`), since the builder only autosaves a song that has been saved once.

## The Studio page (/studio)

`/studio` is the Studio for every visitor, as a real page of the site (no frame, no dialog), and **it is one of the kit's app pages** (the first entry of `APP_PAGES`, see App pages below): a built-in nav link, reserved slugs `studio` and `studio-app`, listed in the sitemap, its content one `#studio-mount`. `public/studio.js` is only what is the Studio's own; it registers with `public/app-kit.js` (shell classes `app-native studio-native`, the parking is `#app-parking`):
- **The editor is the owner's song builder.** The kit takes `#song-builder-modal`, `#songs-modal` (hidden for good) and `#song-audio-modal` from `/admin/index.html` (the studio adds a hidden `#songs-btn` in `prepare`) and loads the song scripts. The admin stylesheet is the kit's scoped copy (`.app-native`); the Studio's part of `public/app-kit.css` makes the editor fill the room under the nav instead of floating and hides owner-only bits (usage, cover art, help, the Songs list's close).
- **The shelf** (`.studio-shelf`) is what shows while the editor is closed: the builder's own New song, starter chips (from `#song-template-picker`'s `starter:` options), Open a song file / Open MIDI (the builder's buttons and inputs, moved in with their ids), and a card per song (a mini picture of its five tracks, Play on the card through `SongEngine.createPlayer`, Copy, Delete; tapping opens it by clicking the hidden list's `.edit-song`). The editor's × is relabelled **Songs** and goes back to the shelf; `saveBeforeShelf` saves first, so it never asks "discard?".
- **The store:** `K.addApi` answers the editor's calls from localStorage (`studio.songs.v1`, `studio.templates.v1`: songs, templates of kind song, duplicate, delete; the kit answers `/settings` and `/content-usage`). Nothing is sent to the server. Never change those two keys: they hold visitors' songs.

- **The builder's markup lives in `public/admin/index.html`**: if that page is ever restructured, keep those ids (or move the markup to a shared file and load it from both); `tests/app-pages.test.mjs` fails when an app asks for a dialog id that is not on the admin page. Something the builder looks up at start that is not inside those three dialogs has to be added in `prepare`.

## App pages (Studio, PicEditor, Simulations, Scans)

Admin tools as pages every visitor can use, built on **`public/app-kit.js`** (`window.SiteAppKit`) with
`public/app-kit.css`. Each one is an entry in `worker/app-pages.js` (`APP_PAGES`: path, nav slug, words, `mountId`, script; `index.js`
routes them, `render.js` adds `/app-kit.js` + the app script, `sitemap.js` lists them), a built-in nav link (`BUILTIN_NAV` in
`worker/nav-settings.js` and `BUILTIN_NAV_LINKS` in app.js), a reserved slug (`db.js`), and its script in page-slide's `LOADABLE`.
- **The kit:** fetches `/admin/index.html` and `/admin/style.css` once for all apps, adds the admin styles **scoped under `.app-native`** (body →
  `.app-shell`) plus `app-kit.css` in one `<style id="app-kit-css" data-added-by>`, takes the app's dialogs out of the admin page, loads its
  scripts once, and `register(app)` runs the page life (boot on the mount, park in `#app-parking` on `site:arrive`, place back on return,
  `window.siteInitApps` called from `siteInitContent`, warm while idle on other pages). The editor's calls are answered in the browser:
  `addApi(fn(path, method, body, query))` (each app's handler is asked in turn; return `undefined` for a path that is not yours), `addFetch` for `fetch("/api/admin/…")`, `addMediaFetch(fn(key))` for `/media/local-…` files, `presetApi(path, key)` for
  named presets in localStorage, `fileStore(db)` for files in IndexedDB. Nothing is sent to the server.
- **PicEditor (`/piceditor`, `public/piceditor.js`):** the photo editor (`#photo-editor-modal`, `#photo-editor-prompt-modal`, scripts
  `photo-color.js` + `photo-editor.js`). Pictures live in IndexedDB `piceditor-pictures`. Save as new = `window.adminUploadBlob` (a new
  picture); a saved picture opens as key `local-<id>` and the editor's Overwrite (relabelled **Save**) is its `PUT /api/admin/media/local-<id>`,

  history, so PicEditor's `park` only sets `aria-modal="false"` (the editor's shortcuts listen only while it is `"true"`). The public CSP

- **Simulations (`/simulations`, `public/simulations.js`):** the circuit builder (`#simulation-builder-modal` plus `#simulations-modal`, kept

- **Scans (`/scans`, `public/scans.js`):** the 3D scan editor (`#scan-editor-modal`, `#scans-modal` kept hidden, hidden `#scans-btn` made in

## Hidden Notes

`/hidden-notes` (owner only; anyone else gets the normal 404) is a vault of notes sealed in the browser (`public/hidden-notes.js`, PBKDF2 then AES-GCM). ## Recipes

- **New admin API route:** add an `if (path === "/thing" && method === …)` block in `routeAdminApi` (use `readJsonBody`, `json`, and
  `log(ctx, env, "create", "thing", name)` for the activity log). If it should be callable from the Scripts window, add the path
  to `WRITABLE` in `public/admin/script-policy.js`.
- **New admin tool/dialog:** markup in `index.html` (sidebar button in a `.admin-sidebar-group`, modal near the others, script tags at the end),
  logic in `app.js` or its own `public/admin/<name>.js`, CSS appended to `public/admin/style.css` using existing tokens (`--bg`, `--bg-elevated`,
  `--border`, `--text-dim`, `--accent`, `--error-text`, `--success`, `--warning`), a command-palette entry (grep `Open Redirects`), a sidebar icon (`#<id> { --ico: … }`).
- **New node type (Scripts window → Nodes):** add it to `NODES` in `public/admin/node-defs.js` (pins, props, and `emit` for a step or `expr` for a value). It
  should call a `site.*` helper (add the helper in `script-runner.js` and `SDK_DOCS` in `script-editor.js` if it is new, and its route to `WRITABLE` in
  `script-policy.js`). `tests/nodes.test.mjs` checks every definition; add a starter graph to `node-templates.js` when it makes a good example.
- **New stored list:** settings rows (rule 2) with routes like `/sections` or `/scripts` (cap the count and the size; validate in a small pure file).
- **New block type / simulation part / song feature:** find the nearest existing one (`grep -n` for a sibling such as `lamp`, `buzzer`, `ties`) and follow it
  end to end: validation → admin UI → public render → CSS → tests.

## The board (features.json)

The admin's Features board is a kanban: **To do** on the left (the owner adds to it), **Working on now** and **Done** on the right. It is driven by
`features.json`: `{"id", "area", "status", "kind", "title", "summary", "notes", "date"}` and a bumped `updated`. Status is `todo`, `doing`, `done` or
`parked`; an open item needs a `kind`: `decision` (waiting on the owner: `notes` must say what to decide), `bug`, `attention`, `almost` or `idea`. Plain
language, no internal item numbers. `node tests/run.mjs features` checks the file.

**The loop:** pick something from `todo` (waiting-on-owner items can't be picked), set it `doing` and push so the owner sees it move; do the work; set it
`done` with `"date": "<today>"` in the same commit as the work; pick the next. Keep two or three `doing` at most. New things you build that were never on
the board get a `done` entry too.

**The owner's own requests** are stored on the live site, which you can't read. They paste "Copy for Claude" output, which lists new requests with ids.
To pick one up add an item with `"request": "<that 12-character id>"`, status `doing`, a `kind`, `"area": "Your requests"` and a note; the board
shows the owner's title with your status. Finish it with `done` + `date`. (An entry whose request no longer exists just shows as a normal item.)

## Working with the owner

Casual, direct, short. Ask when the request is vague instead of guessing. Push back lightly when something doesn't add up. Make a
recommendation instead of listing every option. Ask before anything hard to reverse or outward-facing.
